# Context paging for long assistant sessions: what keeps answers intact at a fraction of the tokens?

Snapshot: 7 Claude Code sessions, 68 questions, 11 conditions, 708 graded answers (`results.md`, generated by
`study/analyze.py`). The `text+recall` row covers 3 sessions so far (28 questions); the background run completes
it and regenerates `results.md`.

## Question

Long sessions fill up with material read once for a side task. On the 38 large sessions on this machine, tool
output is 71.5% of transcript content and what the user and assistant wrote to each other is 2.6%. Can we evict most
of the history and still answer later questions about it? Which way of choosing what to keep works: a decision
model (Kev, an open Jev clone), lexical or dense retrieval, summarisation, or structure?

## Method

- **Data.** 7 real sessions from 5 projects (round-robin by project, largest first). Each contributes its first
  ~240k characters (~60k tokens) of history: user and assistant text, tool calls, tool results. The session that
  designed the study is excluded.
- **Questions without full-context bias.** For each session we sample 14 evidence items (9 tool results, 5
  assistant messages, none pinned, none in the last 10% of the history). Claude writes one follow-up question per
  item from **that item alone**, paraphrased so the question doesn't copy unusual strings from it. We keep 8 to 10
  per session. Each question has one known evidence item.
- **Budget rule shared by every selector.** Every selector always keeps the user's own messages and the last 4
  items. It then adds items in descending score order until 25% of the history's characters is used. Evicted items
  are shown as a one-line stub (`[#id role/kind EVICTED (n chars): first line]`).
- **Conditions.**
  - Baselines: `full`, `compact` (an LLM summary of up to ~2,000 words, which is what auto-compaction does),
    `recency`, `random`.
  - Question-aware selectors, an upper bound because they see the question: `bm25-q`, `embed-q` (bge-small),
    `kev-q` (Kev-0.8B Noul: "does `chunk` help answer `query`?").
  - Blind selectors with paging. These see only the user's last three requests, and the model may answer
    `RECALL: #id…` to page in up to 5 evicted items before answering: `recency+recall`, `kev-task+recall`,
    `stubs+recall` (pinned items only), `text+recall` (all conversation text, no tool calls or output).
- **Answering and grading.** Sonnet answers through headless `claude -p` with no tools, hooks or CLAUDE.md. Opus
  grades blind (0/1/2 against the gold answer) on shuffled rows that hide the condition. Sonnet grades
  independently as a reliability check.
- **Statistics.** 95% CIs come from a cluster bootstrap over sessions (10,000 resamples), because questions within
  a session are not independent. Paired differences use the same resamples. Token counts are the model's reported
  input tokens, summed over both calls when recall happens.

## Results

| condition | score % [95% CI] | input tokens vs full |
|---|---|---|
| full | 98.5 [96.8, 100] | 100% |
| compact | 35.3 [28.7, 41.7] | 4.5% |
| recency | 46.3 [35.6, 57.1] | 35.9% |
| random | 46.3 [28.9, 61.0] | 36.8% |
| bm25-q | 83.1 [67.1, 95.2] | 35.8% |
| embed-q | 84.6 [68.2, 97.1] | 37.7% |
| kev-q | 85.3 [68.4, 97.0] | 38.0% |
| recency+recall | 86.8 [80.0, 92.9] | 58.1% |
| kev-task+recall | 95.6 [91.4, 98.6] | 59.7% |
| stubs+recall | 90.4 [85.7, 94.9] | 40.4% |
| text+recall (3 sessions so far) | 92.9 | 34.3% |

Graders: Opus and Sonnet agree on 99.2% of 708 grades (Cohen's κ = 0.978).

### Findings

1. **Summaries lose the specifics people come back for.** Compaction answered 35% of questions, 63 points below
   full context [57.6, 68.4], and was worse on 46 of 68 questions while beating full on none. File names, byte
   counts, version numbers and exact errors don't survive summarisation.

2. **Paging is the main lever, more than scoring.** Pruning without recall does no better than random (46%).
   Letting the model recall evicted items by id lifts even the crudest policy: `stubs+recall` keeps only what the
   user typed, plus stubs for everything else, and scores 90.4% on 40% of the tokens. Across the three recall
   conditions, the model asked for recall on 41 to 50 of 68 questions and recovered the evicted evidence item 55 to
   60% of the time. The rest of the time it found the fact elsewhere, for example in an assistant message that
   restated it.

3. **When the question is known, the scorer barely matters, and BM25 is free.** Kev, embeddings and BM25 land
   within 2.2 points of each other. Every paired CI includes 0 (Kev minus BM25: +2.2 [−0.8, 5.7]). They all keep
   the evidence item about 70 to 74% of the time at a 25% budget, with AUROC 0.94 to 0.95. Kev costs 385 ms per
   request on an M4 and needs a model server; BM25 takes microseconds. On this data the decision model adds
   nothing measurable over keyword search.

4. **Nobody can predict future questions from the current task.** Blind scorers are near chance at locating the
   evidence item: BM25 AUROC 0.67, embeddings 0.66, and **Kev 0.41, below random**. `kev-task+recall` still scored
   highest of the blind conditions (+8.8 [3.7, 14.0] over `recency+recall`). That gain is **not** explained by Kev
   keeping the evidence: it evicted the evidence item on 63 of 68 questions, against 60 for recency. The effect is
   real, but its cause is unknown; we don't attribute it to Kev's relevance judgement.

5. **Keeping the conversation and stubbing the tool output looks like the best tradeoff, so far.** On the 3
   sessions finished, `text+recall` scores 92.9% at 34% of the tokens. It needs no model at all and is
   deterministic. The final run will report its CI.

6. **Deterministic cleaning isn't worth building for Claude Code.** Stripping HTML/JS and deduplicating lines and
   outputs makes the history 0.4 to 7.5% smaller, because the tools already return mostly text.

### What this means for the original pitch

The real gain in your idea is **evict to stubs and let the model page items back in**. Using a decision model to
rank what to keep added nothing measurable here. The design these results support, in order:

1. Keep the conversation itself and stub every tool call and tool output (`text+recall`).
2. Give the model a recall tool.
3. If something has to be scored, score at ingestion against the tool call's own intent, because that's the one
   moment a real query exists (IDEAS.md #3). BM25 there is a strong, free baseline that any learned scorer has to
   beat.

## Limitations

- **One user, 7 sessions, 68 questions.** CIs for the question-aware selectors are wide (±15 points), because the
  sessions differ a lot from each other.
- **Point-lookup questions only.** Each question needs one fact from one item. Questions that synthesise across
  many items would hurt every eviction policy more and paging less predictably. Not measured.
- **Single evidence label.** Facts are often restated elsewhere, so "evidence recall" understates how often the
  information survived. End-to-end scores account for this; the retrieval table does not.
- **Recall token cost is an upper bound.** The second call re-sends the whole paged context. With prompt caching,
  most of it would be read from cache.
- **Kev-0.8B, not Jev.** The 4B and larger Kev models need more RAM than this Mac has, and Jev was not tested at
  your request. Jev may well do better. The blind-scoring failure (AUROC 0.41) looks like a problem with the task,
  not just model size, but that's untested.
- **Answerer and judge are both Claude.** The two judges agree almost perfectly, but most answers are either the
  exact fact or "NOT FOUND", so grading was easy. Subtle partial answers aren't stress-tested.
- **The history window is ~60k tokens, not a full million-token session.** The effects should grow with length;
  that's untested.
